# ADR-001 - Low-risk architecture for profile calorie estimate and UI/macro fixes

## Context
The CR requests three focused improvements: profile setup calorie estimate clarity, plus button alignment, and duplicate percent-symbol prevention in macro fields. The codebase already has suitable layers (`OnboardingViewModel`, `GoalComputationService`, `SettingsViewModel`, `MainActivity` scaffold) and persistence stores canonical numeric macro values. The main risk is introducing regressions by over-refactoring UI/input paths.

## Decision
Adopt an incremental architecture-preserving approach:
- Reuse existing `GoalComputationService` and onboarding state model for calorie estimate behavior.
- Introduce a shared percent-formatting contract at UI boundary (normalize input, single-suffix display) while keeping repository values numeric.
- Correct plus button alignment only in `MainActivity` scaffold by harmonizing FAB center placement and bottom bar center spacing.
- Keep localization/resource changes minimal and aligned with Italian business intent.

## Alternatives considered
- Alternative A: Full onboarding/settings form component refactor with new custom input controls.
  - Rejected: larger change surface, higher regression probability, unnecessary for CR scope.
- Alternative B: Patch each screen independently with ad hoc string replacements and local logic.
  - Rejected: duplicates logic, raises inconsistency risk across onboarding/settings, harder maintenance.
- Alternative C: Move calorie estimate computation into repository and persist intermediate states.
  - Rejected: violates current separation (domain service computes, repository persists final settings), adds complexity without CR value.

## Consequences
- Positive:
  - Limited blast radius and faster delivery.
  - Consistent percent behavior across two screens.
  - Preserves existing domain formulas and persistence model.
- Negative:
  - Existing UI state string model remains (technical debt not fully removed).
  - Some behavior depends on disciplined usage of formatter helper in all relevant fields.

## Notes
- This ADR intentionally avoids schema migrations, navigation rewrites, or new modules.
- If future CRs expand nutrition input complexity, consider a dedicated reusable input component package as a follow-up ADR.
