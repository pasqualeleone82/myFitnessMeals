# ADR-001: Nutrient Storage Pattern (Per-100g in Food vs Per-Portion in Meals)

## Context

We need to store 12 nutrients (4 base macronutrients + 8 enriched: saturated fat, sugar, minerals, vitamins) for foods and meals. The baseline nutrient data comes from the OFF (Open Food Facts) API, which provides per-100g values. When a user logs a meal, they specify a quantity (e.g., 150g of food). We must decide:

1. **Option A**: Store per-100g values only in `FoodItemEntity`; compute totals on-the-fly during display/save
2. **Option B**: Store both per-100g in `FoodItemEntity` AND denormalized totals in `MealEntryEntity`
3. **Option C**: Store totals only in `MealEntryEntity`; never persist per-100g in meal entry
4. **Option D**: Store per-portion totals in `MealEntryEntity` during save; allow user override per meal

## Decision

**Option B + Option D hybrid**: 
- Store per-100g values in `FoodItemEntity` (new 8 nutrient columns, nullable for OFF compatibility)
- Store denormalized per-portion totals in `MealEntryEntity` (new 8 columns, recomputed at save time based on portion)
- Allow user overrides via `NutritionOverrideEntity` (applies per-food, affects all meals with that food or override per-meal if needed)
- Compute totals at save time; never query-time computation for aggregates

## Alternatives Considered

**Option A (compute on-the-fly)**
- ✅ Pro: Minimal DB footprint; single source of truth per-100g values
- ✅ Pro: No denormalization issues
- ❌ Con: Slow History queries (must join 90 meals × multiply values); not cache-friendly
- ❌ Con: Daily summary queries expensive (aggregation in code, not DB)
- ❌ Con: Difficult to handle user overrides per-meal (no persistent totals)

**Option C (totals only)**
- ✅ Pro: Fast History queries (totals pre-computed)
- ❌ Con: Lose per-100g source data; cannot retroactively fix OFF data errors
- ❌ Con: If user edits food metadata later, old meal entries stale
- ❌ Con: Export/audit requires reverse-engineering totals back to source

**Option D alone (no per-100g in meal entry)**
- ✅ Pro: Smaller meal entry entity
- ❌ Con: Cannot rebuild meal totals if food data corrected (stale meals)
- ❌ Con: Override logic becomes complex (per-food override vs per-meal delta)

## Consequences

✅ **Immediate Benefits**:
- Fast History queries: aggregations pre-computed in `DailySummaryEntity`
- User overrides storable per-food (`NutritionOverrideEntity`) or per-meal (computed delta)
- Historical data immutable (meal totals never recalculated retroactively)
- OFF data updates only affect new meals going forward

⚠️ **Tradeoffs**:
- **Schema size**: +8 columns in `MealEntryEntity` (reasonable)
- **Denormalization risk**: If per-100g food data updated, old meals don't reflect it. **Mitigation**: Document this as expected behavior; encourage users to re-log if OFF data corrects
- **Override complexity**: Need clear precedence (user override > OFF data for totals)
- **Computation at save**: NutrientResolverService responsible; must handle nulls gracefully

✅ **Supports**:
- Swipe navigation (no query performance issues)
- Edit flow (meal totals recomputed from current per-100g when edited)
- Override dialog (override applies to new totals; old meals unaffected unless re-edited)
- Off-line operation (no need to hit OFF API during display)

## Notes

- `DailySummaryEntity` is a denormalized cache; always recalculated post-transaction
- NutrientResolverService is the single source of computation logic; all save/edit/override flows use it
- Migration: new columns in `FoodItemEntity` and `MealEntryEntity` are nullable; backward-compatible
- Test coverage: verify linear scaling (double portion = double nutrients) and null handling (OFF incomplete data)
