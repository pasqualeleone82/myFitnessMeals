# ADR-002: Swipe Gesture Handling (Compose Native vs Custom Detector)

## Context

History tab requires swipe-based day navigation (swipe right = previous day, swipe left = next day). We must decide on the gesture detection mechanism in Jetpack Compose:

1. **Option A**: Use Compose's built-in `detectHorizontalDragGestures` from `androidx.compose.foundation.gestures`
2. **Option B**: Use Material 3's `GestureScope` or similar high-level API
3. **Option C**: Implement custom gesture detector with velocity/distance thresholds
4. **Option D**: Use View-based GestureDetector (pre-Compose, fallback)

## Decision

**Option A** (`detectHorizontalDragGestures`):
- Wrap LazyColumn or root Column with `pointerInput` modifier
- Detect drag velocity and distance; threshold at 400 dp/s and 50 dp min distance
- Emit swipe events to ViewModel
- Provide fallback buttons (Previous/Next) for accessibility

## Alternatives Considered

**Option B (Material 3 GestureScope)**
- ✅ Pro: Higher-level API, consistent with Material design
- ❌ Con: May not provide velocity detection needed for natural feel
- ❌ Con: Overkill for simple left/right navigation (not a slider state)

**Option C (custom detector)**
- ✅ Pro: Full control; can fine-tune thresholds per device
- ✅ Pro: Could support multi-tap gestures in future
- ❌ Con: More code; harder to maintain; easy to introduce bugs (flick vs drag disambiguation)
- ❌ Con: Compose already provides building blocks; custom adds complexity

**Option D (View-based GestureDetector)**
- ✅ Pro: Proven API; many examples
- ❌ Con: Breaks Compose-native architecture; mixes paradigms
- ❌ Con: Performance overhead (View hierarchy interop)

## Consequences

✅ **Benefits**:
- Idiomatic Compose code; no View interop
- Lightweight; leverages Compose's gesture engine
- Compatible with Compose's frame-rate and recomposition model
- Easy to test (can mock pointerInput events)

⚠️ **Tradeoffs**:
- **Fine-tuning**: Velocity/distance thresholds may need adjustment based on user feedback (e.g., too sensitive)
- **User feedback**: Must provide visual feedback (swipe in progress animation) to confirm gesture registered
- **Accessibility**: Swipe-only breaks screen reader usage; must preserve Previous/Next buttons visible (or via keyboard)

✅ **Supports**:
- Smooth day-to-day navigation (~300 ms response time target)
- Debouncing swipes (ViewModel prevents duplicate swipes mid-transition; `isSwipeInProgress` flag)
- Optional fallback buttons (never hidden; always functional)

## Notes

- `pointerInput(Unit)` key ensures gesture detector re-created only on recomposition
- Swipe direction determined by drag offset: `x < -50 dp` = left swipe (next day), `x > 50 dp` = right swipe (previous day)
- Velocity check: `dragEvent.velocity.x.absoluteValue > 400 dp/s` for quick confirmation (not required, but nice-to-have)
- Debounce: set `isSwipeInProgress = true` during animation; ignore input for ~300 ms
- Material 3 ripple feedback still applied to buttons/cards (standard Material behavior)
