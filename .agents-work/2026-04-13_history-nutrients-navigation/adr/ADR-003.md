# ADR-003: Nutrient Override Button Placement & Scope (Per-Meal vs Per-Food)

## Context

Users need to correct nutrient values when OFF data is inaccurate. We must decide:

1. **Button placement**: Inline within nutrient text vs separate button below meal card
2. **Override scope**: One correction per food (all meals affected) vs per-meal correction (this meal only)
3. **UI flow**: Modal dialog edit mode vs dedicated override dialog

## Decision

**Separate button** (labeled "Modifica valori nutrizionali") below meal card + **per-food scope** (`NutritionOverrideEntity`):
- Override stored in `NutritionOverrideEntity` (one per food, applies to all meals with that food)
- Button clearly positioned outside nutrient text (prevents accidental access)
- Dialog shows all 12 nutrients with current values pre-populated
- Override creates audit trail (createdAt, updatedAt in entity)

## Alternatives Considered

**Inline edit (tap nutrient cell to edit)**
- ✅ Pro: Discoverable; immediate context
- ❌ Con: Easy to accidentally trigger; clutters meal card
- ❌ Con: Inline state management (which nutrient in edit mode?) complex in Compose
- ❌ Con: Screen space constrained on History card

**Per-meal override (different from per-food)**
- ✅ Pro: Precise control; one mistake per meal can be corrected
- ✅ Pro: Doesn't affect other meals with same food
- ❌ Con: Requires new DB entity or extended MealEntryEntity (schema bloat)
- ❌ Con: If food corrected in OFF, user must re-override every meal manually
- ❌ Con: Confusing UX (which override applies? per-meal or per-food?)

**Diff/delta mode (override only changed nutrients)**
- ✅ Pro: Conservative; only correct what's wrong
- ❌ Con: Complex UI; users confused about "base vs delta"
- ❌ Con: Difficult to explain (easy to store full value instead)

## Consequences

✅ **Benefits**:
- Clear button = low accidental trigger risk
- ONE override per food = simple mental model for users
- Audit trail built-in (createdAt, updatedAt)
- Reusable override across all meals with that food

⚠️ **Tradeoffs**:
- **User workflow**: If OFF data later corrected, user's old meals still use override (not retroactive)
- **UI complexity**: Must show "Override source" indicator (OFF vs Manual) on meal card
- **Multiple overrides**: If same food overridden twice (one for carbs, one for protein), both fields updated together (no partial overrides)

✅ **Supports**:
- Simple data model (reuse `NutritionOverrideEntity`)
- Single source of truth per food
- Easy to implement tests (assertion: override applied to all meals with same food)

## Notes

- Override precedence: `NutritionOverrideEntity` values > `FoodItemEntity` per-100g
- If override has NULL in a nutrient, fall back to OFF value (not 0.0)
- UI hint: "Modifica valori nutrizionali" button should have an icon (e.g., pencil 🖊️) + text
- Accessibility: Button must be keyboard-focusable and screen-reader-labeled
- Future: If per-meal corrections needed later, add new entity `MealNutrientOverrideEntity` and update precedence logic
