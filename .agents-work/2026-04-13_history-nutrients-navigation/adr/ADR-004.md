# ADR-004: Migration Strategy for Nullable Nutrient Columns

## Context

We are adding 8 new nutrient columns to `FoodItemEntity`, `MealEntryEntity`, `NutritionOverrideEntity`, and `DailySummaryEntity`. These columns are nullable (to handle incomplete OFF data). We must decide:

1. **Migration approach**: Nullable columns vs default values (0.0)
2. **Backward compatibility**: How to handle old app versions that don't understand new columns
3. **rollback safety**: Can we safely downgrade if migration fails?

## Decision

**Nullable columns** (all new nutrients default to NULL):
- Implement `MIGRATION_2_3` in `AppDatabase.kt`
- Add columns with `ALTER TABLE ... ADD COLUMN ...` (standard Room pattern)
- All columns are `REAL` (Room's Double type) or `REAL NULL`
- Default to NULL; application code handles null checks gracefully
- No data copying/transformation during migration (purely additive)

## Alternatives Considered

**Default values (0.0)**
- ✅ Pro: Simpler queries (no NULL checks needed)
- ✅ Pro: Old entries show "0" instead of "N/A" (may seem less confusing)
- ❌ Con: Misleading (0 != no data; user thinks no nutrition available when really data missing)
- ❌ Con: Aggregations become false-positives (e.g., "Total sugar: 0" = no sugar tracked, not "0 grams sugar")
- ❌ Con: Harder to distinguish OFF data missing from "user ate 0 of this nutrient"

**Lazy migration (create on first read)**
- ✅ Pro: Faster app startup (no migration overhead on launch)
- ❌ Con: Non-deterministic behavior (first user to load History triggers migration; others wait)
- ❌ Con: More complex code; harder to test
- ❌ Con: Risk of race conditions if multiple threads/processes access DB

**Full data migration (populate from OFF on migration)**
- ✅ Pro: New data immediately available (no "N/A" display)
- ❌ Con: Migration slow (network call to OFF API or embedded JSON bloats app)
- ❌ Con: User waits at startup for data population
- ❌ Con: May fail if network unavailable (migration can't proceed)

## Consequences

✅ **Benefits**:
- Fast migration (< 100 ms; schema-only, no data movement)
- No network dependency; migration always succeeds
- Clear distinction: NULL = no data, 0.0 = measured as zero
- Backward compatible: new columns ignored by old app (no schema conflicts)

⚠️ **Tradeoffs**:
- **Code complexity**: Application layer must handle NULL nutrients
  - UI displays "—" or "N/A" for NULL
  - Aggregation queries must use `SUM(COALESCE(nutrient_total, 0))` to avoid NULL propagation
- **Query patterns**: DAOs must be null-safe (already handled in Kotlin with nullable types)
- **Future data**: OFF updates won't backfill old meals (by design; meals are immutable)

✅ **Supports**:
- Downgrade safety: Old app can still read (NULL columns ignored)
- Fast rollout: No startup performance regression
- Incremental data population: New meals include enriched nutrients; old meals remain NULL until user edits

## Notes

- Migration code in `AppDatabase.MIGRATION_2_3`:
  ```kotlin
  val MIGRATION_2_3 = Migration(2, 3) { database ->
      database.execSQL("ALTER TABLE food_item ADD COLUMN saturated_fat_100 REAL")
      database.execSQL("ALTER TABLE food_item ADD COLUMN sugar_100 REAL")
      // ... 8 more ALTER for FoodItem
      database.execSQL("ALTER TABLE meal_entry ADD COLUMN saturated_fat_total REAL")
      database.execSQL("ALTER TABLE meal_entry ADD COLUMN sugar_total REAL")
      // ... 8 more ALTER for MealEntry
      database.execSQL("ALTER TABLE nutrition_override ADD COLUMN saturated_fat_100 REAL")
      // ... 8 more ALTER for OverrideEntity
      database.execSQL("ALTER TABLE daily_summary ADD COLUMN saturated_fat_total REAL")
      // ... 8 more ALTER for DailySummary
  }
  ```
- Test on real migration: Use `AppDatabaseMigrationTest` to verify
  1. Create DB at schema version 2
  2. Insert sample data
  3. Run migration
  4. Assert all data intact; new columns queried as NULL
  5. Insert new data post-migration; verify non-NULL values saved/retrieved
- Downgrade: If app reverts to v2, schema mismatch causes crash (expected; document as incompatible)
